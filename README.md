# Pac-Man

## Description

A complete, playable recreation of the classic arcade game Pac-Man,
built in Python with `pygame` (restricted to the subset of functions
that have a direct MLX equivalent). The game features JSON-based
configuration, procedurally generated mazes via an external
A-Maze-ing package, a persistent highscore system, four ghosts with
a shared chase/flee behavior, and a cheat mode for peer review.

The project is split between two contributors:
- **Person A**: configuration loading, maze/collectible integration,
  player logic, scoring, and highscore persistence.
- **Person B**: rendering, the screen/menu system, ghost AI and
  sprites, cheat mode, and packaging.

## Configuration

The game is configured via a JSON file passed as the sole command
line argument. In addition to standard JSON, lines starting with
`#` are treated as comments and stripped before parsing (see
`config/settings.py::_strip_comments`).

| Key | Meaning | Default |
|---|---|---|
| `highscore_filename` | Path to the persistent highscore file | `highscore.json` |
| `levels` | Array of `{"width": int, "height": int}`, one per level | one 15×15 level |
| `lives` | Starting number of lives | `3` |
| `pacgum` | Number of simple pacgums to place per level | `42` |
| `points_per_pacgum` | Score gained per pacgum | `10` |
| `points_per_super_pacgum` | Score gained per super-pacgum | `50` |
| `points_per_ghost` | Score gained per edible ghost eaten | `200` |
| `seed` | Seed for the deterministic first level | `42` |
| `level_max_time` | Time limit per level, in seconds | `90` |

Any missing, malformed, or out-of-range value is clamped to a safe
default with a warning printed to `stderr` — the game never crashes
on a faulty config file. Unknown keys are ignored. If fewer than 10
levels are provided, additional levels are auto-generated by growing
the last one's dimensions (see `config/settings.py::_ensure_min_levels`).

See `config/config.example.json` for a fully annotated example.

## Highscore

Highscores are stored as a JSON array of `{"name": str, "score": int}`
objects in the file named by `highscore_filename`. The list is:

- Loaded once at startup and whenever the Highscores screen is opened.
- Saved immediately after a successful name entry (Game Over or
  Victory screen).
- Limited to the top 10 entries, sorted by score (descending).
- Validated on both read and write: a corrupt or missing file yields
  an empty list rather than crashing; a name must be 1–10
  alphanumeric characters or spaces, otherwise it is replaced with
  `"UNKNOWN"`.

Implementation: `highscore/manager.py`. We chose plain JSON (over,
say, a database) since the data is small, human-readable, and needs
no querying beyond "give me the top 10" — the simplicity outweighs
the theoretical scalability of a heavier storage format.

## Maze Generation

Mazes are generated by the external **A-Maze-ing** package
(`mazegenerator`), assigned to our team and used as-is, without
modification, per the subject's requirements. `maze/loader.py` is the
sole boundary with that package: it calls `MazeGenerator` with
`perfect=False` (to allow the loops needed for Pac-Man-style
corridors), converts its raw bitmask grid into our own `Cell` objects
(`maze/cell.py`), and locates the player's spawn point and the four
corners used for ghosts and super-pacgums.

- The first level always uses the configured `seed` for reproducible
  generation; every subsequent level is generated with a random seed.
- If generation fails (exception, invalid grid, no path from entry to
  exit), `load_maze` returns `None` and the caller handles it
  gracefully instead of crashing.
- Pacgum and super-pacgum placement (`game/collectables.py`) happens
  after generation: super-pacgums always occupy the four corners; a
  configurable number of simple pacgums are placed at random on the
  remaining eligible corridor cells (excluding the isolated cells that
  form the "42" pattern at the maze's center, and the player's spawn
  cell).

## Implementation

### Graphics library and MLX compliance

The game uses `pygame`, restricted to the subset of functions that
have a direct MLX equivalent:

| pygame function | MLX equivalent |
|---|---|
| `display.set_mode` | `mlx_new_window` |
| `display.flip` | window refresh / `mlx_loop` |
| `draw.rect` / `draw.circle` / `draw.polygon` | manual pixel drawing (`mlx_pixel_put` loop) |
| `surface.fill` / `surface.blit` | `mlx_clear_window` / `mlx_put_image_to_window` |
| `image.load` | `mlx_xpm_file_to_image` (or PNG equivalent) |
| `event.get` + `KEYDOWN` | `mlx_key_hook` / `mlx_hook` |
| `time.Clock().tick` | `mlx_loop_hook` (frame timing) |
| `font.Font` + `.render` | `mlx_string_put` |

`pygame.transform.scale`/`smoothscale` is used once per level, at
load time, to pre-scale sprites to the current tile size — never
inside the per-frame draw loop. It has no direct MLX equivalent; we
consider this acceptable as one-time asset pre-processing rather than
a runtime rendering primitive, but flag it here for the reviewer's
attention.

Explicitly **not used**: `pygame.mixer` (no MLX audio equivalent),
`pygame.sprite` collision helpers (collisions are computed manually
via coordinate comparisons), joystick and networking modules.

### Ghost movement

All four ghosts share a single behavior (chosen for simplicity over
differentiated Blinky/Pinky/Inky/Clyde-style AI): a greedy,
waypoint-based navigation through the maze grid in continuous pixel
space (not a discrete grid-snap), implemented in `game/ghost.py`:

1. At each grid intersection, the ghost lists its open neighboring
   cells (`Cell.is_open`).
2. It picks the neighbor closest to the target cell (the player's
   position) when chasing, or farthest when edible (fleeing after a
   super-pacgum).
3. To prevent oscillation between two cells, the previously occupied
   cell is excluded from candidates unless it is the only option
   (a genuine dead end).
4. Movement between waypoints is a straight-line interpolation at a
   speed proportional to the current tile size, so ghosts move at a
   consistent perceived speed regardless of maze size.

This is not optimal pathfinding (no lookahead out of dead ends), but
satisfies the subject's requirement to "define the chase behavior"
while keeping the implementation simple and shared across all ghosts.

Eaten ghosts (`Ghost.get_eaten`) disappear for a fixed respawn delay,
then reappear at their original corner, alive and no longer edible.

### Player movement

The player advances one grid cell at a time on a fixed interval
(`game/player.py`), independent from ghosts' continuous movement.
Turns are buffered: a requested direction is stored and applied as
soon as the next cell in that direction is open, allowing the player
to "pre-turn" before reaching an intersection. `move_progress`
tracks how far the player is between its previous and current cell,
which the renderer uses to interpolate a smooth visual position
between discrete steps.

### Screen architecture (State pattern)

The UI is built around a `Screen` abstract base class
(`ui/screens/base.py`) with three methods every concrete screen
implements: `handle_event`, `update`, `draw`. A `ScreenName` enum
identifies each possible state (`MENU`, `PLAYING`, `PAUSED`,
`GAME_OVER`, `VICTORY`, `HIGHSCORES`, `INSTRUCTIONS`, `EXIT`).

`RenderLoop` (`ui/render_loop.py`) owns every screen instance in a
dictionary and delegates each frame's `handle_event`/`update`/`draw`
calls to whichever screen is current. When a screen's `update()`
returns a `ScreenName`, `RenderLoop.switch_to_screen` performs the
transition — including special cases:

- Pausing keeps the in-progress `PlayingScreen` instance alive in a
  backup slot rather than discarding it, so **Resume** restores the
  exact game state (score, lives, ghost positions, timer).
- Starting a new game from the menu always creates a fresh
  `PlayingScreen`; the paused backup is cleared, so returning to the
  menu can never accidentally resume a previous run.
- `GameOverScreen`/`VictoryScreen` are (re)created with the real final
  score read from the just-ended `PlayingScreen`.

`GameOverScreen` and `VictoryScreen` share their name-entry and
highscore-saving logic through a common base class,
`ScoreEntryScreen`, differing only in title text and color.

## General Software Architecture

```
config/            Config loading & validation (Person A)
├── settings.py    JSON-with-comments parser, defaults, clamping

maze/              Maze representation & generation (Person A)
├── cell.py        Cell: walls + collectible content
└── loader.py      A-Maze-ing integration boundary; Maze class

game/              Game logic
├── player.py      Player position, movement, lives (Person A)
├── collectables.py  Pacgum/super-pacgum placement & consumption (A)
├── scoring.py     Score accumulation (Person A)
├── progression.py Standalone Game state machine, used outside the
│                  pygame UI layer (levels, timer, win/lose) (A)
├── ghost.py       Ghost movement, edible/eaten state (Person B)
└── maze_adapter.py  Legacy prototype, not currently used — flagged
                   for removal, see note in the file itself.

highscore/         Persistent highscore storage (Person A)
└── manager.py     Load/save/validate/add highscore entries

ui/                Rendering & screens (Person B)
├── render_loop.py Owns the pygame window & the screen state machine
├── draw_ghosts.py Ghost sprite loading & rendering
├── draw_player.py Player sprite loading (sheet cutting, rotation)
└── screens/
    ├── base.py               Screen ABC + ScreenName enum
    ├── menu_screen.py         Main menu
    ├── playing_screen.py      Core gameplay loop
    ├── pause_screen.py        Pause overlay
    ├── highscores_screen.py   Highscore list
    ├── instructions_screen.py Controls/rules
    ├── score_entry_screen.py  Shared name-entry base class
    ├── game_over_screen.py    Game Over (extends ScoreEntryScreen)
    └── victory_screen.py      Victory (extends ScoreEntryScreen)

assets/            Sprites (ghosts, Pac-Man sprite sheet)
tests/manual/      Manual visual test harnesses (not graded)
docs/              Project management artifacts
```

`PlayingScreen` (`ui/screens/playing_screen.py`) is the integration
point between the two contributors' work: it owns the `Maze`,
`Player`, `CollectibleManager`, and the four `Ghost` instances for
the current level, drives their per-frame updates, and renders them
together with the HUD.

AI assistance (Claude) was used throughout this activity, primarily
for:

- **Architecture guidance**: discussing and comparing design options
  before implementation — e.g. choosing the State pattern for
  screens over a flat if/elif dispatcher, and comparing waypoint-based
  ghost movement against alternatives — with the final decisions and
  their justification always made and understood by us.
- **Debugging**: diagnosing specific runtime bugs (e.g. an
  uninitialized-attribute ordering bug, a ghost oscillation caused by
  a missing "don't backtrack" rule, a `mypy` type-narrowing issue in
  the render loop) by walking through the actual error and the
  relevant code together, rather than being handed a fix blind.
- **Linting compliance**: reviewing existing code against `flake8`/
  `mypy` rules from the Makefile's `lint` target, and explaining the
  reasoning behind each fix (e.g. why an unannotated `None` attribute
  breaks type-checking, why a keyword argument shouldn't have spaces
  around `=`).
- **Scaffolding**: generating boilerplate/skeleton code (screen class
  stubs, a manual test harness) that was then filled in, reviewed,
  and adjusted by us — per the project's own rule of not accepting
  ready-made game logic without understanding it.

All AI-assisted code was reviewed, tested, and is understood by both
team members; peer review within the team was used as a check on top
of this, consistent with the activity's AI usage guidelines.
